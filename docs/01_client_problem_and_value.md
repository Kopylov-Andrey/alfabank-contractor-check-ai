# Проверка контрагента: проблема клиента и ценность решения

**Статус:** актуальная версия под фактическую архитектуру (Yandex AI Studio + Yandex Cloud)
**Дата:** 4 сентября 2026 года
**Назначение:** зафиксировать пользователя, его задачу и проверяемую ценность решения — приведено в соответствие с тем, что реально реализовано и запланировано в AI Studio/Yandex Cloud.

## 1. Кто пользователь

**Основной пользователь MVP — закупщик или менеджер юридического лица**, который проверяет нового поставщика, подрядчика или другого делового партнёра.

`[Факт кейса]` Клиенты банка уже получают отчёт с регистрационными, контактными, финансовыми, судебными и реестровыми сведениями. Отчёты становятся длиннее, а компании проверяются по одной.

`[Гипотеза]` Наиболее остро проблема проявляется у сотрудника, который отвечает за сделку, но не занимается профессиональным риск-анализом.

## 2. Контекст, триггер и задача

**Контекст:** у сотрудника есть потенциальный контрагент и банковский отчёт о нём.
**Триггер:** заключение договора, проведение оплаты или выбор поставщика.
**Задача:** быстро подготовить проверяемую основу для решения внутри компании: понять факты из отчёта, ограничения данных и необходимые дополнительные проверки.

**Рабочая формулировка на основе кейса:** сократить ручное чтение отчёта, быстро увидеть подтверждённые факты и понять, что ещё проверить до сделки.

## 4. Текущий путь и боли

`[Гипотеза]` Ниже представлена рабочая модель текущего пути на основе кейса. Она не подтверждена пользовательскими исследованиями.

| Шаг сейчас | Что делает пользователь | Боль — гипотеза |
|---|---|---|
| 1. Находит компанию | Ищет по названию или ИНН | Может выбрать не ту запись |
| 2. Открывает отчёт | Последовательно просматривает разделы | Факты распределены по длинному документу |
| 3. Интерпретирует | Сам связывает финансы, суды, реестры и индикаторы | Неясно, что важно перед конкретной сделкой |
| 4. Уточняет | Возвращается к разделам или обращается к коллегам | Простой вопрос требует повторного поиска |
| 5. Определяет следующий шаг | Сам составляет список проверок | Можно пропустить пробел или принять отсутствие сведений за хороший сигнал |

`[Гипотеза]` Главная потеря — время на поиск и интерпретацию, а не отсутствие ещё одного скоринга.

## 5. Ценностное предложение

**AI-агент, собранный на Yandex AI Studio (Agent Atelier), превращает один или несколько отчётов в короткую проверяемую сводку:** заполняет предопределённые информационные блоки, отвечает на вопросы по данным отчёта, показывает основания в тексте ответа, отмечает пробелы и предлагает нейтральные следующие проверки.

`[Решение]` Агент подключён к двум инструментам напрямую в AI Studio: **MCP-серверу** с доступом к базе отчётов контрагентов (поиск, получение отчёта по ИНН, сравнение нескольких компаний) и **Web Search** для дополнения ответа сведениями из открытых источников, когда это уместно. Данные отчёта остаются основным и приоритетным источником: если веб-поиск возвращает что-то, что расходится с отчётом, агент явно помечает это как «по данным открытых источников» и не подменяет факт отчёта.

Помощник **не** рассчитывает собственный рейтинг и **не** говорит «работать / не работать». Решение остаётся за пользователем и ответственными сотрудниками компании.

1. **Клиент:** меньше ручного чтения; быстрее понятны факты, ограничения и следующий шаг; может сравнить нескольких контрагентов в одном диалоге.
2. **Банк:** подтверждённая полезность может создать предпосылку для повторного использования; фактическое влияние пока не измерено.
3. **Надёжность AI:** приоритет — данные отчёта; веб-поиск используется только как явно помеченное дополнение. `[Известное ограничение]` Эта граница обеспечивается на уровне системного промпта агента, а не отдельной серверной проверкой — подробнее в документе 05.

## 6. Основной сценарий одной проверки

1. Пользователь называет компанию по названию или ИНН в чате с агентом.
2. Агент через MCP-инструмент находит и получает отчёт (при неоднозначном названии — уточняет).
3. Агент формирует сводку по предопределённым блокам и явно показывает ограничения данных.
4. При необходимости агент дополняет ответ данными из веб-поиска, чётко обозначая их как внешний источник.
5. Пользователь задаёт уточняющий вопрос в том же диалоге.
6. Пользователь получает ответ, основания в тексте, ограничения и нейтральный следующий шаг.
7. При необходимости пользователь просит сравнить нескольких контрагентов в одной сессии — агент вызывает инструмент сравнения.

## 7. Связь пользовательской и банковской ценности

| Уровень | Метрика | Статус в хакатоне |
|---|---|---|
| Пользователь быстрее понимает отчёт | Время задачи и точность найденных фактов | Не измеряется на реальных пользователях |
| Пользователь перепроверяет ответ | Проверки с ≥1 подтверждаемым основанием / проверки с готовым ответом | Проверяется вручную по эталонному набору (документ 04) |
| Пользователь использует диалог | Проверки с ≥1 вопросом / проверки с показанной сводкой | Можно заложить событие, результат не заявляется |
| Организация возвращается | 28-дневная доля повторных проверок | Не измеряется в хакатоне |

**Завершённая проверка** — сессия, в которой пользователь назвал компанию и успешно получил сводку. **28-дневное повторное использование** — доля организаций, которые после первой завершённой проверки получили сводку по другому ИНН в течение 28 дней. Цель нельзя задать без исходного значения текущего продукта.

`[Гипотеза]` Сводка, чат и основания могут сократить время понимания отчёта минимум на 30% без ухудшения точности. `[Факт текущего статуса]` В хакатоне этот эффект и повторное использование не измеряются, поэтому их нельзя считать подтверждёнными.

| Допущение | Как проверяем | Предлагаемый порог |
|---|---|---|
| `[Гипотеза]` Закупщик/менеджер — главный пользователь | В хакатоне не проверяется | Не измерено |

| `[Гипотеза]` Ответы агента можно перепроверить по отчёту | Ручная сверка по эталонному набору вопросов | ≥95% фактических утверждений подтверждены |
| `[Гипотеза]` Нейтральные действия безопаснее вердикта | Ручная проверка всех рекомендаций в тестовом наборе | 100% рекомендаций нейтральны; 0 вердиктов |

## Что нужно подтвердить до финала

- Фактические результаты проверки прототипа на реальном агенте с подключёнными MCP и Web Search.
