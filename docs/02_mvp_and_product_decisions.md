# MVP и продуктовые решения

**Статус:** актуальная версия под фактическую архитектуру (Yandex AI Studio + Yandex Cloud)
**Дата:** 4 сентября 2026 года
**Назначение:** зафиксировать границы MVP исходя из того, что реально собрано в AI Studio, и показать, как продуктовые решения определяют реализацию и проверку.

## 1. MVP: «Контрагент — по фактам»

**AI-агент в Yandex AI Studio с доступом к базе отчётов через MCP и к открытым источникам через Web Search.** Перед договором, оплатой или выбором поставщика он формирует структурированную сводку, отвечает на вопросы, помогает сравнить нескольких контрагентов и определить следующий шаг.

Это не «чат ради чата»: агент не заменяет исходный отчёт, не создаёт собственный скоринг и не принимает решение за клиента.

`[Факт кейса]` Агент должен использовать входные данные и не выдумывать информацию. Интеграция с банковскими системами и большая внешняя база не входят в границы задачи.

`[Решение]` В отличие от более раннего варианта, где MCP и веб-поиск планировались только за закрытым серверным контуром, в реализованной версии **оба инструмента подключены напрямую к агенту в Agent Atelier**. Это заметно ускорило и упростило реализацию, но означает, что изоляция «одна компания за сессию» и приоритет данных отчёта над веб-поиском обеспечиваются системным промптом, а не отдельным сервером — см. раздел 9 «Известные ограничения».

## 2. Основной пользовательский сценарий

**Пользователь называет компанию (по названию или ИНН) в чате с агентом → агент через MCP находит и получает отчёт → сводка → вопрос → ответ с основаниями, при необходимости дополненный веб-поиском → нейтральный следующий шаг**

При неоднозначном названии агент вызывает инструмент поиска и уточняет у пользователя, какую компанию он имеет в виду, прежде чем формировать сводку. При явной просьбе сравнить нескольких контрагентов агент вызывает инструмент сравнения в рамках той же сессии.

## 3. Границы MVP

| Must — обязательно | Should — при наличии времени после порога готовности | Won't — не входит в MVP |
|---|---|---|
| Поиск и получение отчёта по ИНН через MCP-инструмент `get-report-by-inn` | Поиск по названию/отрасли через `search-contractors` | Автоматическое «работать / не работать» |
| Сводка по заданным блокам | Копирование сводки | Собственный риск-скоринг |
| Общий риск и ЗСК раздельно | Оценка «полезно / не полезно» | Объяснение неизвестной формулы риска |
| Чат по выбранному отчёту в рамках сессии | Сравнение нескольких компаний через `compare-contractors` | Интеграция с банковскими системами |
| Явная обработка ограничений данных | Подсказки типовых вопросов | Юридическая, финансовая или комплаенс-консультация |
| Нейтральные следующие проверки (текстом, по шаблону из промпта) | Веб-поиск как явно помеченное дополнение (уже подключён) | Рекомендации банковских сервисов |
| | | Серверная валидация путей/значений — целевая архитектура, не в текущем MVP |

`[Решение]` Сравнение нескольких контрагентов и веб-поиск, которые в более ранней версии документа считались вне скоупа, **реально реализованы и подключены** — перенесены в Should/Must, потому что уже работают, а не потому что решение о скоупе изменилось задним числом без причины: команда посчитала, что раз MCP уже даёт доступ к нескольким компаниям через `compare-contractors`, отключать эту возможность искусственно не имеет смысла.

## 4. Состав сводки и фактического ответа

Модель не ранжирует компании и не определяет риск самостоятельно. Сводка заполняется по предопределённым блокам:

1. Статус компании и дата отчёта.
2. Общий риск и ЗСК — как отдельные значения из отчёта.
3. Юридические сведения: суды, производства, проверки и лицензии (если есть в отчёте).
4. Финансовые значения и динамика по доступным периодам.
5. Репутационные факторы.
6. Ограничения и пробелы данных.
7. При наличии релевантных сведений — краткое дополнение из веб-поиска, отдельным пунктом, явно подписанным «по данным открытых источников».

AI не решает сам, какой факт «главный». Продукт заранее задаёт состав сводки и правила ответа в системном промпте.

- **Фактический тезис** — любое утверждение агента о компании, значении, событии, наличии или отсутствии данных. Для каждого такого тезиса агент должен указать, откуда он взят (раздел отчёта или веб-поиск).
- **Ожидаемый факт** — информация, которая прямо отвечает на тестовый вопрос и присутствует в отчёте. Для него заранее указываются одно или несколько обязательных полей-оснований; разметку проверяет второй участник.
- **Существенный тезис** — заранее отмеченный человеком факт, ошибка в котором может изменить понимание ситуации: статус, индикатор риска, сумма, дата, судебное или реестровое событие. Неподтверждённый существенный тезис считается критической ошибкой.

## 5. Функциональные требования

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-1 | Поиск и выбор | При неоднозначном названии агент уточняет у пользователя через диалог; при отсутствии совпадений — сообщает об этом |
| FR-2 | Сводка | Заполнены доступные предопределённые блоки и показана дата отчёта |
| FR-3 | Контекст сессии | Ответ относится к компании, которую пользователь называл в текущем диалоге; при явной смене компании агент работает с новой компанией |
| FR-4 | Основания в тексте | Ответ агента указывает, на какой раздел отчёта или источник опирается каждый факт (в свободном тексте, без формального JSON-контракта) |
| FR-5 | Состояния данных | Различаются подтверждённое значение, отсутствие данных, неподтверждаемый вывод |
| FR-6 | Два индикатора | Общий риск и ЗСК показаны отдельно без нового общего балла |
| FR-7 | Следующий шаг | Рекомендация формулируется нейтрально, по одному из четырёх шаблонов из документа 06 |
| FR-8 | Вопрос вне границ | Агент отказывает на вопросы про другую компанию, неизвестную формулу риска и просьбы дать вердикт |
| FR-9 | Веб-поиск | Сведения из Web Search явно помечены как внешние и не заменяют данные отчёта при расхождении |
| FR-10 | Сравнение | При явной просьбе агент вызывает `compare-contractors` и строит сравнение по фактам без сведения к единому скорингу |

Разрешённый каталог следующих шагов (используется как текстовая конвенция в промпте, не проверяется отдельным валидатором):

| Код | Шаблон |
|---|---|
| `REQUEST_DOCUMENT` | Запросить у контрагента `{документ}` |
| `CLARIFY_DISCREPANCY` | Уточнить у контрагента `{расхождение}` |
| `REFRESH_REPORT` | Обновить данные отчёта перед решением |
| `INTERNAL_REVIEW` | Передать факт `{факт}` уполномоченному специалисту компании |

Вердикты, прогнозы, консультации и рекомендации банковских продуктов запрещены системным промптом.

### Семантика пустых значений

Ноль считается нулевым значением только для поля, где это подтверждено схемой. Пустой список, `null` и отсутствующее поле обрабатываются по контракту данных (см. документ 06). Пустой список означает «записей нет» только при подтверждённых полноте и смысле поля; иначе применяется формулировка «в отчёте нет доступных сведений». Пустота не означает отсутствие риска.

## 6. Нефункциональные требования и порог готовности

Числовые пороги — внутренние критерии команды, а не достигнутые результаты.

| ID | Требование | Предлагаемый критерий |
|---|---|---|
| NFR-1 | Покрытие основаниями | В проверке ≥95% фактических тезисов сопровождаются указанием источника в тексте ответа |
| NFR-2 | Безопасность AI | 0 критических выдумок на тестовом наборе и повторах |
| NFR-3 | Приоритет отчёта над веб-поиском | 0 случаев, когда факт из веб-поиска подан как факт отчёта или его подменил |
| NFR-4 | Безопасный отказ | Неподтверждаемый вывод заменён явным ограничением |
| NFR-5 | Производительность | Время ответа фиксируется по факту; целевой ориентир — не более 10–15 секунд с учётом возможного вызова MCP и Web Search в одном ответе |
| NFR-6 | Воспроизводимость | В тестовом прогоне фиксируются версия системного промпта, версия данных в Object Storage, дата прогона |
| NFR-7 | Устойчивость к подмене инструкций | Пользовательская просьба не изменяет границы агента |

## 7. Ответ агента (текущий формат)

Агент возвращает **свободный текст в формате Markdown**, структурированный системным промптом по фиксированным разделам:

```text
Сводка: светофор риска + ЗСК, краткий вывод, ключевые риски,
финансы, [дополнение из веб-поиска], рекомендация
Ответ на вопрос: краткий ответ + указание источника
```

`[Известное ограничение]` Это не строгий JSON Schema с отдельными полями `claims`/`evidence`/`data_gaps`, как в целевой инженерной архитектуре — соответствие формату обеспечивается только инструкцией модели, без автоматической серверной проверки. Модель может использовать инструменты MCP и Web Search и не имеет доступа к внешнему поиску, кроме этого явно подключённого инструмента.

## 8. Ключевые продуктовые решения и влияние на реализацию

| Связь | Решение | Пользовательская причина | Влияние на реализацию | Как проверяем |
|---|---|---|---|---|
| H1, H4 | Агент сам ищет и получает отчёт через MCP | Не нужен отдельный backend для MVP | MCP-сервер подключён напрямую к агенту в Agent Atelier | Тесты на смену компании и корректность выбора |
| H1, H4 | Заданные блоки сводки | Понятен состав ответа | Структура задаётся системным промптом | Полнота ожидаемых фактов |
| H2, H3 | Приоритет отчёта, веб-поиск — явное дополнение | Не смешивать источники и даты | Правило в системном промпте, без серверной проверки | 0 случаев подмены факта отчёта |
| H2, H3 | Указание источника в тексте ответа | Ответ можно перепроверить | Инструкция модели «указывай раздел отчёта» | Ручная сверка по эталонному набору |
| H3, H4 | Состояния данных | Пустота не выглядит как «риска нет» | Явные формулировки в промпте | Вопросы с `0`, `null`, `[]` и отсутствующим полем |
| H3 | Общий риск и ЗСК отдельно | Не смешивать разные сигналы | Явное правило в промпте | 5 специальных вопросов |
| H5 | Нейтральные действия | Решение остаётся за человеком | Разрешённый каталог шаблонов, текстовая конвенция | Ручная проверка на вердикты |
| H7 | Сравнение нескольких компаний | Меньше ручного сопоставления | MCP-инструмент `compare-contractors` уже реализован | Тест сравнения 2–3 компаний |

ЗСК относится к риску вовлечённости в подозрительные операции и не является универсальным выводом о надёжности контрагента ([Банк России](https://cbr.ru/counteraction_m_ter/platform_zsk/)).

## 9. Известные ограничения текущей реализации

- MCP-инструмент `get-report-by-inn` принимает произвольный ИНН — технически модель может запросить любую компанию из базы, не только ту, что назвал пользователь. Изоляция «одна компания за диалог» держится только на инструкции агента, а не на серверном ограничении.
- Нет серверного валидатора, который бы проверял пути к полям, точность значений и корректность кодов действий до показа ответа пользователю — весь контроль качества ответа выполняется вручную на этапе тестирования (документ 03/04).
- Приоритет данных отчёта над веб-поиском — тоже правило уровня промпта, не технический барьер: агент физически может обратиться к веб-поиску при любом вопросе, если сочтёт нужным.
- Целевая архитектура с закрытым backend, изолированной сессией и структурированным JSON-контрактом (описанная в более ранней версии документа 05) остаётся направлением развития после хакатона, а не частью текущего MVP.

## 10. Что увидит пользователь

- Ответ агента в чате с реквизитами компании и датой отчёта.
- Сводку по заданным блокам и два раздельных риск-индикатора.
- Возможность задать уточняющий вопрос и получить ответ с указанием источника.
- Ограничения данных и нейтральные следующие проверки.
- При запросе — сравнение нескольких контрагентов и, при необходимости, краткое дополнение из открытых источников.
